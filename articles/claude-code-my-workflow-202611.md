今の自分のやり方の棚卸しです。半年後には変わっていると思うので、2026 年 11 月時点の記録として書きます。

筆者は Web のフロントエンドを中心に 8 年ほど開発をしています。Claude Code は基本的に毎日使っていて、使わない日はほとんどありません。

全体を一言でまとめると、「書くのは AI、疑うのは別の AI、決めるのは自分」です。

## commit と push は自分で打つ

AI にやらせるのは、編集、`git add`、検証、コミットメッセージの案までです。commit と push は自分で打ちます。

AI に commit と push を任せていた時に失敗したことがあります。作業ブランチの追跡先（upstream）が別のブランチに付いたままになっていて、気づかないまま、そのブランチに push してしまいました。入った先はリリース用のブランチです。push した直後に「あれ、おかしくないか」と気づいて、レビューに出す前に force push で戻しました。

それからは自分が見ていない変更が共有のブランチに出ないように push は自分で打っています。push の直前は自分が diff を読む最後の機会でもあります。

## メインは監督、手を動かすのはサブエージェント

自分と直接話すメインのセッションには実装をさせません。

| 役割 | モデル | やること |
| --- | --- | --- |
| 自分と話す相手（メイン）・相談役 | Fable | 要件の整理、作業の分割、依頼、返ってきた diff の検収 |
| 進め方を考える役・調査役 | Opus | どう実装するかを考える、原因の調査、リスクの判定 |
| 実装役 | Sonnet | 実装、テストの生成、定型の修正 |

Opus が「こう実装する」と決めて、Sonnet が実際に書く、という分担です。

メインに実装までさせていた頃はトークンをかなり食っていました。実装や調査を Opus や Sonnet のサブエージェントに下ろしていったら、使う量が減りました。

サブエージェントを使う時の決まりは 3 つです。

- 起動する時はモデルを必ず指定する。省略するとメインと同じモデルで動く
- 依頼文はそれだけ読めば作業できるように書く。背景、対象のファイル、期待する出力、制約を入れる。サブエージェントはこちらの会話を知らない
- 返ってきた実装はメインが必ず diff を読む

よく使う役はエージェントの定義でモデルを固定しています。定義は Markdown のファイル 1 つで、先頭にこう書きます。

```markdown
---
name: implementation-coder
description: 決まった方針の範囲だけをテストを先に書いて実装する
model: sonnet
---
```

数行の修正なら、メインが直接やります。迷ったら任せます。

## バグ修正は段階に分けて、順番に回す

原因の見立てが外れたことは何度もあります。モデルの性能が今より低かった頃に周辺の調査をさせないまま、雑に「直して」と投げていた時がそうでした。原因を取り違えたまま直すと、別の所から再発します。そこでバグ修正の流れをスキル（`bugfix-pipeline` と呼んでいます）にまとめました。

| 段階 | 担当 | 次へ進む条件 |
| --- | --- | --- |
| 起票 | メイン | 同じ件の過去の記録が無いかを確かめた |
| 原因の調査 | 調査役（`incident-investigator`） | 原因に至る経路を説明できる |
| 方針の決定 | メインと自分（`select-approach`） | 自分が方針に合意した |
| 実装 | 実装役（`implementation-coder`） | 失敗するテストを先に書き、通るまでの記録がある |
| 検収 | メインと自分 | 残っているリスクを自分が見た |

一番効いているのは原因の調査を別の文脈に出す所です。調査役には症状とコードの範囲だけを渡します。メインが立てた「原因はこれだろう」という見立ては渡しません。

原因も直し方も分かっているつもりの時ほど、何も知らない調査役に調べ直させます。

方針の決定には必ず自分が入ります。案を複数出させて、手間・影響の範囲・リスクを並べてもらい、自分が選びます。合意の前に実装へ進まない、を決まりにしています。

## レビューは実装を知らない 2 つの目に任せる

実装したセッションの AI にレビューさせると、自分の前提に引っ張られます。そこで、実装が終わったら、会話を共有していない 2 つのレビューを同時に走らせる仕組みを作りました。

- 独立した Claude。会話の履歴を持たない、読み取り専用のレビュー用エージェント
- Codex CLI の `codex review`。別の会社のモデルに同じ差分を見せる

Claude 側への依頼文はわざと短くしています。

```text
リポジトリ: <絶対パス>
対象: 未コミットの変更
対象ファイル: 全体
要件: <コードだけでは正しい動きが決まらない時だけ短く>
```

実装の経緯や「ここは大丈夫なはず」という説明は書きません。書くと、レビューする側も同じ前提に染まります。

返ってきた指摘はそのまま直させません。メインに指摘が当たっているかを確かめさせてから、当たっているものだけ直します。確かめ方は 2 つあります。実際に動かして再現するかを見ることと、コードを読んで指摘の言っていることが合っているかを見ることです。

作った文脈から切り離して壊しにいかせる、という考え方は [「敵対的検証」として紹介されている物](https://zenn.dev/little_hand_s/articles/6aa18c80496ec6)と同じです。自分の仕組みでは同じ差分を 2 つの会社のモデルに同時に見せて、どちらが何を見つけたかを記録する形にしました。

2026 年 11 月 18 日にこの仕組みを 2 回走らせました。対象は個人で作った Next.js のサイトです。

| 回 | 差分 | 指摘 | Claude だけ | Codex だけ | 両方 | 直した |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 公開ページを作り置きに切り替えて画像を最適化に通す変更（約 30 ファイル） | 5 | 3 | 0 | 2 | 3 |
| 2 | 1 ファイルの小さな修正 | 1 | 1 | 0 | 0 | 0 |

1 回目で一番重かった指摘は独立した Claude だけが挙げました。画像の最適化を有効にすると、管理画面で URL を直接入力した外部の画像が許可した配信元から外れて表示されなくなる、という物です。実装したセッションが見落としていた所で、直しました。

両方が挙げた 2 件は、開発環境でローカル保存の画像が出なくなる問題と、足したテストがデータ次第で落ちる問題です。こちらも直しました。

2 回の合計で指摘は 6 件です。確かめて外れだった指摘は 0 件、Codex だけが見つけた指摘も 0 件でした。直さなかった 3 件はどれも優先度が一番低い指摘です。

記録は 10 タスク分ためて、そこで Codex を続けるかを決めます。

## 失敗はルールにして残す。ただし思い出すことに頼らない

AI がやらかした失敗はその場でルールの文書に足します。大きく 2 種類あります。

- 作業のしかたのルール。「想定外の状態を見つけたら、推測で片付けずに一言聞く」「分からないことを分かったように書かない」など
- 差分を見直す時の点検項目。過去に見逃したコードの間違いを積み上げたもの

ただ、ルールを足すだけでは同じ失敗がまた起きます。ルールは AI がその場面で思い出して初めて効くからです。

同じ失敗が 2 回起きたら、ルールを厚くするのをやめて、hook（PreToolUse）で機械的に止める側に移しています。今、止めているのは次の操作です。

- git の push と、コミットを作る操作
- `origin/` を起点にしたブランチの作成。後の push が起点のブランチを書き換える原因になる
- まだコミットしていない変更を捨てる操作（`reset --hard` など）。捨てる変更が実際にある時だけ止める

登録は `~/.claude/settings.json` に書きます。判定のスクリプトは長くなるので、ここでは登録の形だけ載せます。

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash|PowerShell",
        "hooks": [
          { "type": "command", "command": "python", "args": ["/path/to/guard.py"], "timeout": 15 }
        ]
      }
    ]
  }
}
```

止める時は理由と代わりの手順を AI に返します。止めるだけだと、AI は別の書き方で同じことをしようとします。たとえば、`origin/` を起点にしたブランチ作成を止めた時は、こう返します。

```text
起点に origin/release を付けたブランチ作成を止めた。追跡先が起点のブランチに張られ、
後の push が起点を書き換える原因になる。起点のブランチを checkout してから、
起点を省略して git checkout -b fix/a で作る。
```

## 頼まれたら、答える前にチケットを切る

AI との会話は次のセッションに引き継がれません。自分も 2 か月前のことはほとんど覚えていません。

作業が発生したら、AI に最初にチケット（Markdown のファイル 1 つ）を作らせます。進むたびに追記させます。ひな形の要点だけ抜くと、こうです。

```markdown
---
type: "Task Ticket"
title: ログイン画面のタイムアウト警告の修正
workflow_status: in-progress   # todo / in-progress / blocked / done / dropped
created: 2026-11-18
updated_at: "2026-11-18T10:30:00+09:00"
---

## 背景
なぜやるか。聞いた事実だけを書く。

## ゴール
何ができたら完了か。

## TODO
- [ ] …

## 進捗メモ
- 2026-11-18 10:30: 何が分かったか、何で詰まったか、何を決めたか
```

置き場は `task/<名前>/_index.md` です。終わったら、フォルダごと `task/done/` に動かします。

次のセッションではチケットを読ませて続きから始めます。新しい依頼を受けた時はまず過去のチケットを検索させます。前にやった作業を「初めて」として扱わせないためです。

残しておくと、2 か月前に同じような事象があって、根本の原因が同じだった、と分かることがよくあります。チケットを切っていて困ったことは無く、助かったことしかありません。

## 知識は道具に依存しない Markdown で持つ

ルールも、手順も、チケットも普通の Markdown で 1 つのフォルダに置いています。Claude Code のスキルやエージェントの定義は、その Markdown を読みに行くだけの薄いファイルです。

使う道具が変わる前提でこうしています。別の道具に移っても本体の Markdown はそのまま使えます。

各ファイルの先頭の frontmatter は、Google Cloud の [Open Knowledge Format（OKF）](https://github.com/GoogleCloudPlatform/knowledge-catalog/blob/main/okf/SPEC.md) に合わせています。上のチケットの `type` や `updated_at` もその決まりに沿った項目です。

## テストは自分が説明できるまでが検収

AI にテストを書かせると、通るテストはすぐ出てきます。ただ、そのテストが何を守っているのかを自分が分かっていないと、後で意味が無くなります。

AI が書いたテストは、自分が「このテストは何が壊れたら落ちるのか」を一言で言える所までを検収にしています。

やってみると、分かっていなかった所は挙げればきりがありません。AI が書いたテストを前に「これはこういう仕様で大丈夫なんだっけ」と自分に問い直すことになり、どういう仕様にしたかったのかを考え直すきっかけになっています。

AI に一覧表を出させて眺める形は取りません。答えを先に見ると、確認になりません。AI に質問させて、自分が答えます。答えと実際がずれた所だけ説明してもらいます。

## うまくいっていないこと

ルールを足しすぎて、ルール同士が矛盾したことがあります。その時はルールを全部並べてから、整理し直しました。

モデルも道具もすぐ変わるので、このやり方もまた変わると思います。
